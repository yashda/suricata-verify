# fw-intent-tls-sni-minimal-rules

Integration fixture demonstrating that combining three firewall-intent keyword
features lets an author express a TLS-SNI allow-list intent in exactly **2 rules**
where the upstream baseline requires **~13 rules**.

## Features exercised (all three must be present in the linked suricata binary)

| Feature | Rule | Syntax used |
| --- | --- | --- |
| Multi-value TCP session lifecycle | Rule 1 | `tcp.session:setup,established` |
| Multi-value app-layer-protocol | Rule 1 | `app-layer-protocol:unknown\|tls` |
| Walker `<` operator (prior-state auto-accept) | Rule 2 | `tls:<client_hello_done` |

Note on syntax: The multi-value `app-layer-protocol:` keyword uses the pipe (`|`)
separator per the parser convention already established in
`app-layer-protocol-negated-list` and `app-layer-protocol-unknown-tls-boundary`.
The `tcp.session:` keyword uses a comma-separated value list per the convention
in `tcp-session-equivalence`.

## Baseline comparison

The equivalent intent expressed without these three features requires the ~13-rule
expansion documented in the sibling fixture `fw-prior-state-tls-sni-allow` (on
branch `feat/fw-prior-state-fixtures`):

- 4 TCP handshake rules (SYN, SYN-ACK, ACK, post-handshake passthrough)
- 7 TLS prerequisite rules (`client_in_progress`, `server_in_progress`,
  `server_hello`, `server_cert_done`, `server_hello_done`,
  `server_handshake_done`, `server_finished`)
- 1 Decision_Hook rule that carries the `tls.sni; content:...;` condition
- (Optional 1 accept rule for the flow-close teardown, depending on ruleset style)

This fixture collapses that entire expansion into two author-visible lines by
pushing the transport lifecycle into `tcp.session:`, the app-layer boundary
into multi-value `app-layer-protocol:`, and the state-walk into the `<`
operator.

## What is asserted

1. **Rule load count == 2**: both rules parse and load; none fail. Proves the
   three-way keyword combination compiles.
2. **Permitted SNI accepted**: the TLS flow with SNI `www.google.com` reaches
   `flow.action: "accept"` and closes cleanly.
3. **Zero drops**: no packet in the flow is blocked.
4. **IPS accounting**: `stats.ips.accepted: 62`, `stats.ips.blocked: 0`.

## PCAP

Reuses `../../tls/tls-client-hello-frag-01/dump_mtu300.pcap`, the same
fragmented-ClientHello capture used by the walker-reference fixture
`ruletype-firewall-89-lt-sni`. Contains a single TLS flow with SNI
`www.google.com`.

## Known limitations / TODOs

- **Single-SNI PCAP.** The chosen PCAP contains only one flow with the
  permitted SNI. To also exercise the drop-by-default path (a second flow
  with a non-permitted SNI that should be blocked by the absence of a
  matching `accept:flow` rule) a mixed-SNI PCAP would be required. Either:
  1. Reuse the `.amazon.com` PCAP generated by
     `fw-prior-state-tls-sni-allow/gen_pcap.py` (branch
     `feat/fw-prior-state-fixtures`) plus a synthesized second flow with a
     non-permitted SNI, or
  2. Generate a fresh PCAP under this fixture with two TLS flows using scapy.

  This is intentionally left as a follow-up so the fixture demonstrates the
  positive path first without depending on cross-branch PCAP fetches.

- **Implementation dependency.** This fixture is authored ahead of full
  integration of the three keyword features into upstream `suricata`. It
  will only run green once the following spec tasks land in the linked
  suricata binary:

  | Feature | Spec task |
  | --- | --- |
  | `tcp.session:` keyword | tasks 5–8 in `.kiro/specs/firewall-intent-rules-app-layer-and-transport-shortening/tasks.md` |
  | Multi-value `app-layer-protocol:` | tasks 9–11 in the same spec |
  | Walker `<` operator | already present in upstream |

  Until the underlying implementation lands, the fixture is expected to
  fail at rule load (Rule 1 will not parse if either `tcp.session:` or the
  multi-value form of `app-layer-protocol:` is not compiled in).
