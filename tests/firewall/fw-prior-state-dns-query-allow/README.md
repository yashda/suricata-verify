# fw-prior-state-dns-query-allow

POC Suricata-verify fixture for task 8.2 (spec:
`.kiro/specs/firewall-rule-templates/tasks.md`).

Exercises the Intent-Based Firewall Rules auto-accept-prior-states POC
pipeline end-to-end against real packets on **both** DNS transports
(UDP and TCP). One Prior_State_Rule using the `<` operator targets
`dns:request_complete`, with an author condition matching DNS query
suffix `.amazon.com`.

## What this validates

- **Multi-transport expansion for a protocol registered on both TCP
  and UDP.** Suricata registers DNS on both transports
  (`rust/src/dns/dns.rs:1282` for UDP, `:1329` for TCP), both
  resolving to `ALPROTO_DNS`. The expander emits the 4-rule TCP
  handshake block (sub indices 1..4) followed by the 2-rule UDP
  bidirectional block (sub indices 5..6) in the stable `{TCP, UDP}`
  order described in design §Expansion Algorithm Step 2, so a single
  Prior_State_Rule permits the flow regardless of which transport the
  traffic actually arrives on (Requirements 1.3, 1.5).
- **State-machine identification for a built-in-hook-only protocol.**
  DNS registers no named states with the app-layer parser; the
  registry synthesises the four built-in hooks (`request_started`,
  `request_complete`, `response_started`, `response_complete`) from
  completion-status values (Requirement 5.1 / 6.1, design
  §Components.3).
- **Bidirectional expansion for `:tx` on a protocol whose registry
  exposes only built-in hooks.** The author writes one rule at
  `request_complete`; the expander emits `request_started` (TOSERVER
  prereq, sub 7), plus `response_started` and `response_complete`
  (opposite direction up to completion, subs 8 and 9), plus the
  Decision_Hook rule itself (Requirement 3.1, design §Worked Example
  DNS query allow-list).
- **Author's condition preserved at the Decision_Hook.** The
  `dns.query; content:".amazon.com"; endswith;` tail is carried onto
  the single emitted Decision_Hook rule verbatim (Requirement 1.2).
- **Customer-facing SID abstraction.** Every eve alert record fires
  under the author's Parent_SID 3003; no derived Sub_SID leaks to
  customer-facing output; no `metadata.expanded_from` field appears in
  any record (design Decision 2 / Requirements 7.3, 7.4).

## Files

- `test.rules` — one-line Prior_State_Rule (operator form), no
  `alert;` keyword (the Decision_Hook rule relies on the engine's
  default silent-accept behaviour for `accept:tx`).
- `suricata.yaml` — firewall mode + eve.json / fast.log outputs.
- `input.pcap` — synthesized multi-transport DNS capture:
  1. UDP query + NOERROR response on port 53 for `www.amazon.com`
     (2 packets).
  2. A DNS-over-TCP flow on a distinct client port: full 3-way
     handshake, DNS query with the RFC 1035 §4.2.2 2-byte
     big-endian length prefix, server ACK, DNS response with length
     prefix, client ACK, and a FIN/FIN-ACK teardown (10 packets).

  Generated by `gen_pcap.py` (kept in-tree for reproducibility — the
  packets are synthetic on purpose so the fixture does not depend on
  external DNS servers or network state).
- `gen_pcap.py` — regenerate `input.pcap` via
  `python3 gen_pcap.py`.
- `test.yaml` — asserts `sid:3003` fires once per DNS query (UDP and
  TCP, for a total of 2 alerts), no drop events, no Sub_SID leak into
  customer-facing eve records, no `metadata.expanded_from` field, and
  that both DNS request records land with the expected query name.

## Relation to the in-tree implementation

If the in-tree expander at the time of the task 9 exit gate does not
yet iterate the full transport set (for example, if it only emits the
handshake for one representative transport per protocol), the TCP
query in this fixture will not be accepted through the `packet_filter`
table and the multi-transport assertions will fail. The fixture
matches the design as of task 8 — surfaces that discrepancy at the
task 9 exit gate for the user to act on.
