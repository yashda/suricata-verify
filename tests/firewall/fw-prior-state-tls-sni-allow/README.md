# fw-prior-state-tls-sni-allow

POC Suricata-verify fixture for task 8.1 (spec:
`.kiro/specs/firewall-rule-templates/tasks.md`).

Exercises the Intent-Based Firewall Rules auto-accept-prior-states POC
pipeline end-to-end against real packets. One Prior_State_Rule using the
`<` operator targets `tls:client_hello_done`, with an author condition
matching SNI suffix `.amazon.com`.

## What this validates

- **State-machine identification for a TCP-carried named-state
  protocol.** The `client_hello_done` hook is resolved out of the
  app-layer parser's TLS state machine with no TLS-specific code in
  the expander (Requirement 5.5).
- **Transport-handshake emission for TCP.** The 4-rule TCP handshake
  template (SYN, SYN-ACK, ACK, post-handshake passthrough) is
  stitched onto the author's five-tuple and gates the handshake
  through the `packet_filter` table (Requirement 1.3, design
  §Expansion Algorithm Step 2).
- **Bidirectional expansion for `:tx` scope.** Both client-side prior
  states (just `client_in_progress`) and every server-side state up
  to completion (`server_in_progress`, `server_hello`,
  `server_cert_done`, `server_hello_done`, `server_handshake_done`,
  `server_finished`) are auto-accepted (Requirement 3.1, design
  §Worked Example TLS SNI).
- **Author's condition preserved at the Decision_Hook.** The
  `tls.sni; content:".amazon.com"; endswith;` tail is carried through
  the expander verbatim onto the single emitted Decision_Hook rule
  (Requirement 1.2).
- **Customer-facing SID abstraction.** Every eve alert record fires
  under the author's Parent_SID 1003; no derived Sub_SID leaks to
  customer-facing output; no `metadata.expanded_from` field appears
  in any record (design Decision 2 / Requirements 7.3, 7.4).

## Files

- `test.rules` — one-line Prior_State_Rule (operator form), no
  `alert;` keyword (the Decision_Hook rule relies on the engine's
  default silent-accept behaviour for `accept:tx`; customer-facing
  assertions below rely on the *absence* of Sub_SIDs rather than on
  alerts firing).
- `suricata.yaml` — firewall mode + eve.json / fast.log outputs.
- `input.pcap` — synthesized TLS 1.2 flow with SNI `www.amazon.com`:
  TCP 3-way handshake, ClientHello, minimal server response
  (ServerHello + Certificate + ServerHelloDone in one record),
  FIN exchange. Generated by `gen_pcap.py` (kept in-tree for
  reproducibility — the packets are synthetic on purpose so the
  fixture does not depend on an external certificate chain or
  handshake).
- `gen_pcap.py` — regenerate `input.pcap` via
  `python3 gen_pcap.py`.
- `test.yaml` — asserts `sid:1003` fires exactly once with
  `tls.sni: "www.amazon.com"`, no drop events, no Sub_SID leak into
  customer-facing eve records, and no `metadata.expanded_from` field.

## Relation to the in-tree implementation

The fixture's assertions match the design as of task 8. If the
in-tree expander at the time of the task 9 exit gate does not yet
append `noalert;` to every auto-accepted Expanded_Rule, a packet
traversing a TLS prerequisite rule can generate an alert record whose
`signature_id` is a derived Sub_SID (high bit set). The Sub_SID-leak
assertion in `test.yaml` will catch that regression at the task 9
exit gate.
